# Fair-division learning site — design

## Goal and audience

Build a public, shareable bilingual (Traditional Chinese and English) learning site for colleagues unfamiliar with fair division of indivisible goods. Visitors should learn what EF1, EFX, and Nash social welfare (NSW) mean by judging allocations before seeing formal results, creating cases, and competing to find allocations with high NSW. Anonymous visitor ratings let colleagues compare mathematical criteria with people's initial intuitions; these convenience-sample results are not representative research findings.

## Scope and learning flow

1. **Guided examples:** A small curated set of nonnegative additive-valuation cases introduces people, indivisible items, values, allocations, envy, EF1, EFX, and NSW. A visitor rates a proposed allocation on a 1–5 scale from very unfair to very fair **before** seeing any formal scores or classification. After submission, show explanations, aggregate ratings, and a link to try another example.
2. **Create a case:** A visitor enters agents, indivisible items, and a nonnegative integer value for each agent-item pair. Each item must belong to exactly one agent in any submitted allocation. Publishing produces an immutable, shareable case URL; editing values requires publishing a new case. Include clear input validation and a preview before publishing.
3. **Compete within a case:** Visitors to a case can assign every item to an agent, submit allocations, and see a leaderboard ranked by raw NSW. A reproducible randomized round-robin allocation serves as a baseline: use a stored random seed for the agent order, then each agent picks their most-valued remaining item on their turn, breaking ties by item order. Baseline allocations are visually labeled and are not attributed to visitors. All allocations use the same case values, so their raw NSW scores are comparable.
4. **Judge then reveal:** For each proposed allocation, the fairness question is shown without EF1/EFX classifications, NSW, rank, aggregate votes, or fractional comparison. On submitting a 1–5 rating, reveal its scores, explanation, and aggregate rating distribution. If the visitor has already rated it in this browser, reveal the result without accepting another vote from that browser. This is a friction measure, not proof of unique respondents.
5. **Learn the computational distinction:** Explain that evaluating a given allocation's NSW is straightforward, while finding an NSW-maximizing indivisible allocation is computationally hard (the appropriate decision version is NP-complete). Explain EF1 existence for additive nonnegative goods, without implying that the analogous EFX existence statement follows. Avoid presenting a heuristic or a fractional solution as the indivisible optimum.

## Language and localization

- The first release supports Traditional Chinese (`zh-TW`) and English (`en`) across navigation, lesson text, rating labels, mathematical explanations, validation errors, loading states, and result summaries. Use browser language for the initial choice (Traditional Chinese for `zh-TW`, otherwise English); provide a visible manual language switch and retain the visitor's choice in the browser.
- Both languages share the same cases, IDs, submitted allocations, votes, metrics, and leaderboard; switching language must not duplicate a vote or restart the lesson. Curated explanatory copy is translated in both languages. Visitor-entered agent and item names remain exactly as entered, not machine-translated. Shareable case links work in either language.

## Mathematical model and feedback

- Agent i's bundle value is the sum of their values for its items; values are nonnegative integers. NSW is the **product** of all agents' bundle values. Zero utility for any agent makes NSW zero; equal products tie and are not broken by an unrelated fairness metric. Display large products exactly as decimal integers rather than relying on floating-point multiplication.
- EF1: for every pair of distinct agents i and j, either i does not envy j, or there exists an item in j's bundle whose removal eliminates i's envy. EFX here uses the *positively valued item* convention: for every pair i, j and every item in j's bundle valued positively by i, removing that item eliminates i's envy. Display this convention explicitly and show a witness pair (and relevant item when applicable) for failures.
- Provide individual bundle values and concise reasons for EF1/EFX outcomes. The baseline and user allocations are computed by the same scoring routine on the server; the client can preview changes but never supplies a trusted score.
- Separately compute an **estimated optimal NSW for the same case with fractionally divisible items** by maximizing the product of bundle values under per-item fractions summing to one. This is a relaxation, not the optimal indivisible allocation. Perform the numerical solve as a separate, time-bounded request, cache results by immutable case ID, and label the number as a numerical estimate rather than a certified upper bound when solver precision cannot certify it. If the solver times out, fails, or is too resource-intensive, show “fractional comparison unavailable”; the leaderboard and voting still work. Handle cases whose attainable NSW is zero explicitly. No arbitrary small cap on the number of items or agents is a mathematical rule, but protect public endpoints with payload-size, execution-time, and resource limits.

## Architecture and data

- A web application serves the lesson, case editor, case pages, allocation builder, rating prompt, and results. An **externally managed PostgreSQL database** (for example Supabase) stores curated and visitor-created cases, their valuation matrices and creation timestamps, immutable submitted allocations, their computed metrics, a reproducible baseline seed, anonymous 1–5 ratings, and cached fractional-solver status/result. Case and allocation IDs form shareable URLs.
- Server endpoints validate and publish cases, generate the round-robin baseline, validate and score allocations, accept ratings, and return aggregate rating histograms, counts, and means. Keep scoring logic in one independently tested module. Do not expose database write credentials in the browser; apply server-side validation and access rules to all public writes.
- A separate bounded compute endpoint/service runs the fractional numerical solver only on demand and caches its result. The ordinary page request and leaderboard do not wait for this endpoint. Provide distinct pending, estimated, and unavailable states. The numerical method must respect fractional item constraints and nonnegative utilities.
- **Deployment:** Publish two Docker images and one Docker Compose configuration for a single machine: a Next.js web container serves both pages and API from one public port; a solver container is reachable only on the private Compose network. PostgreSQL remains externally managed and is not started by Compose; only the web container connects to it. Provide reproducible production builds, environment-variable secrets (not baked into images), web and solver health checks, startup dependencies, a repeatable one-off database migration command, and documented logs/restart behavior. The machine's reverse proxy terminates HTTPS and forwards requests to the web container; the solver port is never published. Public accessibility requires an externally reachable database connection and configured DNS/TLS, but neither the database nor the reverse proxy is packaged into these two images.
- Anonymous visitors need no account; collect no names or emails. Store rating value, allocation ID, and timestamp, not IP addresses as survey data. Use browser-local voted-allocation IDs to discourage accidental duplicates; document that determined users can vote repeatedly. Apply rate limits, input-size and numeric bounds, and output escaping to case, allocation, and rating endpoints. These protections also apply to curated examples where relevant.
- Aggregates are per **allocation**, not across allocations with different valuations. Show vote count and 1–5 distribution beside the mean. Do not claim results measure the general public or establish a concept as objectively fair.

## Failure behavior and validation

- Reject malformed matrices, non-integer/negative/out-of-range values, duplicate or missing item assignments, unknown case/allocation IDs, and oversized requests with actionable messages. A case with zero agents or zero items cannot be published. Show a clear retry path on network failure; do not record a vote locally until the server accepts it.
- Publishing and score storage are transactional so an allocation cannot appear without its trusted metrics. Case data remains immutable after publication. For a given browser, keep ratings hidden until its vote has been accepted, even if the aggregate endpoint is available elsewhere; this is a teaching-flow constraint, not a security guarantee.
- Fractional solver failures must not affect other features. Be explicit about unavailable or approximate results rather than displaying misleading precision. If the external database is unavailable, web readiness fails and write APIs return a retriable service-unavailable response rather than implying a successful vote or case publish.

## Verification

- Unit-test NSW (including zero and very large products), EF1 and EFX (including zero-valued goods and witness explanations), valuation sums, allocation validation, and deterministic round-robin tie breaking against hand-worked cases.
- Test fractional solver constraints and known tiny cases against analytical answers; test timeout/unavailable paths without blocking the rest of the experience.
- Integration-test create → publish → share → submit allocation → rate before reveal → aggregate → leaderboard and ensure ratings and metrics are not shown before the rating step in the intended interface. Test malformed requests, abuse limits, and repeated browser votes.
- Review the lesson text in both languages for the distinction between computing NSW and optimizing it, EF1 existence assumptions, EFX convention, and survey limitations. Test both full learning/rating flows, browser-language default, manual switching and persistence, shared links, and translated error and solver-status states.
- Build and boot the two production images using Compose against a disposable external PostgreSQL instance; apply migrations with the documented one-off command, confirm the web container serves a real frontend page and API on the published port, confirm the solver is not host-exposed, and verify health checks, restart behavior, and graceful database/solver outage handling.

## Out of scope for first release

Accounts, durable one-person-one-vote guarantees, representative statistical inference, cross-case NSW rankings, certified optimal indivisible NSW, unrestricted compute time, and editable published cases.
